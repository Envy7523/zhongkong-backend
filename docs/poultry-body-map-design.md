# 鹅部位示意图 + 份量自检 · 设计说明（供外部评审）

> 用途：把「整只出成拆解」的配置从纯文字表格改成**可视化 + 守恒校验**，降低禽类部位份量系数配错的风险。
> 本文自包含，读完即可评审，不需要其他上下文。

---

## 0. 一句话概括

在烧味连锁店的「菜品核算」系统里，新增一张**可点选的 SVG 鹅部位示意图** + 一个**份量自检面板**，
让运营人员在配置「一只鹅出几个部位、每个部位占多少份量」时，能**用图形理解结构、用守恒校验即时发现填错**，
而不是等算完只数、跟门店日报对不上才发现问题。

---

## 1. 业务背景

- 客户：「鹅太公烧鹅」连锁烧味店，21+ 门店
- 痛点：门店每天手工记录**整鹅消耗只数**并上报；老板想从收银系统的**菜品销量**自动反推某门店某时间段消耗了多少只鹅（用于对账、控损、估成本）
- 系统里只有「卖了多少份菜」，**没有「一份菜用掉多少只鹅」** → 必须先建三层基础档案：
  ① 禽类档案（一只鹅）→ ② 整只出成拆解（一只鹅出哪些部位、各占多少份量）→ ③ 菜品耗用（每份菜吃掉几个部位）

## 2. 领域知识（理解本设计的前提）

### 2.1 一只鹅的物理拆解

```
一只鹅 = 上半身 1/2 + 下半身 1/2
  上半身 = 2 个上庄（每个 1/4 只，各自带 1 只翅）
  下半身 = 2 个下庄（每个 1/4 只，各自带 1 条腿）
  另有：鹅头带颈 1 个、鹅腩 1 份
  切片肉：从上下庄取下的肉，用于做烧鹅饭 / 濑粉 / 双拼 / 三宝饭
```

### 2.2 「一只出几份」的语义（项目里最大的坑）

该字段 = **一只鹅能出几份这种"份量"的菜** = `1 ÷ (一份占整只的比例)`

| 部位 | 一份占整只 | 「一只出几份」应填 |
|---|---|---|
| 上庄 | 1/4 | **4** |
| 下庄 | 1/4 | **4** |
| 鹅腿 | 1/8（腿占下庄一半；一份 = 一整条腿） | **8** |
| 半只 | 1/2 | **2** |
| 整只 | 1 | **1** |
| 鹅肉（切片做饭） | 1/11 | **11** |

⚠️ **最容易错成"数块数"**：一只鹅确实只有 **2 块**上庄，但这个字段要填**份量倒数 4**。
填 2 等于说"一份上庄吃掉半只鹅"，会把同一只鹅在上庄、下庄里各算一次 → 结果虚高近一倍。

### 2.3 部位的两类性质

| 类别 | 包含 | 计算规则 | 理由 |
|---|---|---|---|
| **身体类** | 整只 / 半只 / 上庄 / 下庄 / 腿 / 腩 / 切片肉 | 需求**相加** | 同一块身体的不同卖法，互相抢鸟（卖了整只就不能再卖它的下庄） |
| **副产品** | 头颈 / 翅 / 掌 / 杂 / 肝 / 肠 | 需求**取最大** | 一只鸟同时产出，不额外占鸟 |

### 2.4 核算公式（料篮模型）

```
demand_p        = Σ(该部位的菜品销量 × 每份耗用)
body_birds      = Σ_{身体}   demand_p ÷ parts_per_bird_p     ← 相加
byproduct_birds = max_{副产品}(demand_p ÷ parts_per_bird_p)   ← 取最大
N               = max(body_birds, byproduct_birds)           ← 总只数
```

## 3. 本次新增的功能

### 3.1 整只部位示意图（SVG，可点选）

**布局**（俯视示意，非解剖精确图）：

```
            ┌──────┐
            │ 头+颈 │
    ┌──┐  ┌─┴──────┴─┐  ┌──┐
    │翅│  │  上  庄  │  │翅│          ← 翅在两侧（上庄自带翅）
    └──┘  ├──────────┤  └──┘
          │  下  庄  │                ← 下庄自带腿
          ├───┬──────┤
          │腩 │      │
    ┌──┐  └───┴──────┘  ┌──┐
    │腿│                │腿│
    └──┘                └──┘
  ┌──────────────────────────┐
  │ 切片肉区（鹅肉/小料/双拼/三宝饭）│
  └──────────────────────────┘
  另有：整只/半只 → 罩住全图的虚线外框
```

**配色即语义**：

| 颜色 | 含义 |
|---|---|
| 🔵 蓝 | 身体类（相加） |
| 🟠 橙 | 副产品（取最大） |
| 🟢 绿 | 切片肉区（多个部位共用一块区域） |
| ⚪ 灰虚线 | **该部位还没配置** |
| 加粗描边 | 当前点选中 |

每个区域上直接标注：`部位名 一只出N份（=1/N）`

### 3.2 份量自检（核心价值）

图表右侧面板，实时校验两条「份量守恒」：

| 检查项 | 判据 | 不通过时的提示 |
|---|---|---|
| ① **上庄 2 块 + 下庄 2 块 = 一整只身体** | 合计应恰好 = 100%（容差 ±3%） | >100%：「超过一只，可能把『数块数』当成了份量口径」<br><100%：「不足一只，可能有部位没登记，或份量填大了」 |
| ② **腿 2 条应含在下庄之内** | 腿合计 ÷ 下庄合计 落在 15%~80% | ≥80%：「腿几乎等于整个下庄，检查是否该填『一只出 8』」<br>≤15%：「腿份量偏小，检查系数是否填大」 |
| ③ 副产品（翅 / 头颈） | 恒通过，仅标注说明 | 「按数块数填写，不参与份量守恒」 |

### 3.3 点选联动

点图上的部位 → 下方表格对应行**高亮** + 顶部提示「已定位：鹅腿（一只出 8 份）」；
点到未配置区域 → 提示「该区域还没有配置部位，可用『新增部位』补一行」。

## 4. 实现逻辑（技术细节）

### 4.1 组件

```
frontend/src/components/PoultryBodyMap.vue
props:  rows（当前出成行数组，含 part_name / parts_per_bird / part_kind）
        animal（鹅/鸭/鸡，用于标题）
emit:   pick（点击某区域 → 父组件拿到该区域的部位行，用于高亮表格）
```
纯展示 + 计算组件，**不写数据库**；配置保存仍走原来的表格与接口。

### 4.2 部位名 → 图示区域的归类（正则关键词，按优先级）

```js
function zoneOf(name) {
  if (/头|颈/.test(n))                    return 'head'    // 头+颈
  if (/翅|战斧/.test(n))                  return 'wing'    // 翅（战斧=大鹅翅）
  if (/上庄/.test(n))                     return 'upper'
  if (/下庄/.test(n))                     return 'lower'
  if (/腩/.test(n))                       return 'belly'
  if (/腿|肶/.test(n))                    return 'leg'
  if (/整只|一只|半只|整鹅|半鹅/.test(n))  return 'whole'   // 虚线外框
  if (/肉|小料|双拼|三宝|片/.test(n))      return 'meat'    // 切片肉区
  return 'other'
}
```

### 4.3 份量自检的计算式

```js
// 某区域在一只禽中的总份量占比 = Σ(块数 ÷ 一只出份数)
function totalShare(zone, pieces) {
  return rows.filter(r => zoneOf(r.part_name) === zone)
             .map(r => pieces / r.parts_per_bird)
             .reduce((a, b) => a + b, 0)
}

// 检查①：上下半身守恒（一只鹅 2 块上庄 + 2 块下庄）
const sum = totalShare('upper', 2) + totalShare('lower', 2)
ok = Math.abs(sum - 1) < 0.03

// 检查②：腿含在下庄之内（一只鹅 2 条腿）
const ratio = totalShare('leg', 2) / totalShare('lower', 2)
ok = ratio > 0.15 && ratio < 0.8
```

### 4.4 集成位置与配套缺陷修复

- 位置：菜品核算页 → 基础档案抽屉 → **② 整只出成拆解** 页签顶部
- 同时修了一个既有 bug：`App.vue` 用了 `<KeepAlive :max="30">`，从「堂食菜品绑定」页返回核算页时组件不重新 mount，
  导致「缺口明细」里已绑好的菜仍显示为缺口 →
  新增 `onActivated()` 钩子（页面每次激活即重取核算结果）+「查看缺口明细」改为先刷新再开弹窗

## 5. 实测验证

### 5.1 自检的检测能力（用真实配置回测，不需要浏览器）

| 配置 | 检查① 上下庄合计 | 检查② 腿占下庄 |
|---|---|---|
| 鹅腿 = **8**（正确值） | 100% ✅ | 50% ✅ 正常 |
| 鹅腿 = **4**（曾经的错误值） | 100% ✅ | **100% ⚠ 提示「检查是否该填一只出 8」** |

→ 结论：这个自检**能在配置阶段就抓到那个导致 +15% 偏差的错误**。

### 5.2 配套的端到端校准数据

门店「欧景花园店」2026-09-01 ~ 09-10，门店日报记录 **80 只鹅**（口径：当天实际消耗的整鹅数，无统计误差）：

| 鹅腿系数 | 算出的总只数 | 与门店日报偏差 |
|---|---|---|
| 4 | 92.13 只 | **+15.2%** |
| 6 | 85.05 只 | +6.3% |
| **8** | **81.51 只** | **+1.9%** ✅ |
| 10 | 79.38 只 | −0.8% |
| 12 | 77.96 只 | −2.6% |

其余 11 个部位的系数完全没动，只调「鹅腿」一个数，偏差就从 +15.2% 收敛到 +1.9%。

## 6. 已知争议点 / 待评审（请重点看这一节）

### 6.1 「整只 / 半只」与「上庄 / 下庄」的份量重叠

- 现状：`整只=1`、`半只=2`、`上庄=4`、`下庄=4`，全部归"身体类"相加
- 物理关系：一只 = 2 上庄 + 2 下庄（含头颈/翅/腿）；半只 = 1 上庄 + 1 下庄
- **用户补充**：「一只自然是一整只鹅，**半只就不包含鹅头带颈**」
  → 严格算：半只应是 `(100% − 头颈占比) ÷ 2 ≈ 45.5%`，即「一只出」应填 **2.2** 而不是 2
  → 实测影响：半只 12 份 × (1/2 − 1/2.2) ≈ **0.64 只**（81.51 → 80.87，反而更贴门店 80）
  → 而头颈作为**副产品**（取最大）本来就不会被重复相加，所以现状没有重复计算问题
- **待评审**：是否应把「整只 / 半只」这类打包部位改为**用菜品耗用拆开配**？
  即：`太公烧鹅·整只` 配成 `上庄×2 + 下庄×2`，`太公烧鹅·半只` 配成 `上庄×1 + 下庄×1`
  —— 这样"半只天然不含头颈"，份量天然正确，不需要人工把 2 改成 2.2

### 6.2 副产品用「数块数」填、身体类用「份量倒数」填 —— 两套口径混用

- 头颈填 1（一只鹅 1 个头颈）、翅填 2（一只鹅 2 只翅）→ 语义是**块数**
- 身体类填 4 / 8 / 2 → 语义是**份量倒数**
- 为什么副产品用块数是对的：副产品折鸟 = `demand ÷ parts_per_bird`，
  例：头颈卖 32 份 ÷ 1 = 32 只 → 语义"32 个头颈需要 32 只鹅"✅
  若按份量口径（头颈约占整鹅 9%，一只出 11）→ 32 ÷ 11 = 2.9 只，语义错误
- **待评审**：同一个字段承载两种口径是否合理？是否该在 UI 上对副产品**单独分列**（如"一只出几块" vs "一只出几份"），
  或在数据结构上分两个字段？

### 6.3 切片肉四个部位是否互斥

- `鹅肉`（一只出 11）、`小料`（17.5）、`双拼`（23）、`三宝饭`（29）目前都归"身体类"**相加**
- 若它们取自**同一块切片肉**（只是装盒不同）→ 相加会高估
- 若为**不同等级/部位**的肉 → 相加正确
- 用户尚未确认 → **待评审**：数据模型上如何表达"同一块肉的不同装盒"？
  （可能的思路：引入"共享部位组"，组内取最大而非相加）

### 6.4 自检阈值的选择

- `|上下庄合计 − 1| < 0.03`、`0.15 < 腿/下庄 < 0.8` 均为经验值
- **待评审**：是否有更合理的判据（例如按生物学比例区间、或按门店实际称重数据反推合理区间）

### 6.5 部位名归类依赖正则关键词

- 用户可自定义部位名（如「鹅腿」也可能写成「鹅肶」）
- 当前靠关键词匹配归到图示区域，未匹配的落到 `other`（图上不显示）
- **待评审**：是否应在数据层给部位加一个「图示区域」枚举字段（而非运行时猜），更稳但增加配置负担

## 7. 技术栈与项目约束

- 前端 Vue 3 + Element Plus；后端 Express + sql.js（SQLite，纯 JS/WASM）
- 数据表：`poultry_birds`（禽类档案）/ `poultry_yields`（整只出成拆解）/ `poultry_dish_usage`（菜品耗用）/ `poultry_purchases`（实际采购）
- 项目硬约束：
  - 验证脚本**绝不允许整表 DELETE**，只能用自建临时数据并回收；改配置需先快照、后原样还原
  - 改核算算法后，**7 条核算不变量**必须仍成立
    （每行只数 = 销量×每份耗用÷一只出成；部位折鸟 = 总需求÷一只出成；只数 = max(身体相加, 副产品最大)；
     合计 = 各禽之和；每禽唯一瓶颈标注；旧口径 ≥ 新口径；明细占比合计 100%）
  - 现有验证：49 项端到端 + 29 项批量关联 + 12 项风控对账 + 13 项出成追加 + 23 项绑定推荐
- 数据边界：`dish_sales`（菜品销售明细）当前只到 2026-09-10

## 为什么长期没有通过

线上十天90项报表的首次终态只有14项成功。此前最终数据恢复不等同于首次自动完成；修复与验收过多依赖补采，没有完整验证跨日、断线、进程退出和关联报表晚到后的行为。

已观察到的线上证据：

- `collector_no_active_source_rows`共142次。11月3日京东营业02:00开始、05:08才取得有效数据，商品06:39；闪购营业和商品03:00开始、07:37及07:38才成功。四项均无此前的远程补采请求。启动时刻与源报表出数时刻不同，不能把空原件当零营业。
- 控件超时98次、控件歧义29次、扩展命令超时17次。菜单、隐藏副本、字段变化和扩展协议都曾造成失败。
- 11月2日闪购结算在03:06因缺同日营业对照停在待核；营业表07:37到达后，动态数据核验能通过，但任务记录仍停在待核。

下列缺陷通过独立故障测试复现，不将每一个潜在问题都声称为历史实际失败原因。

## 本轮修改

| 环节 | 已复现的缺口 | 修正 |
| --- | --- | --- |
| 自动恢复 | 中午后跳过；前一执行日用完8次后永不恢复 | 保留有限退避，按执行日重置预算，恢复最近三个营业日；登录、金额、范围错误不盲目重试 |
| 状态持久化 | 写入任务预约后、写历史前退出，任务永久卡住 | 检查预约缺口；先核对云端原件，再恢复本地任务 |
| 关联核验 | 营业表晚到后商品/结算不再复核 | 依赖指纹变化才调用现有finish复核，保留原失败历史，不重导出 |
| 事件队列 | 永久拒绝的旧事件堵住所有采集；并发flush可能漏发 | 被明确400/409拒绝的诊断隔离保存；队列先持久化、串行发送；401/403不绕过 |
| 成功状态 | 旧失败日志延迟上传能覆盖成功 | 所有finish请求前先排空旧事件，再确认本轮结果 |
| 恢复入口 | 普通重试仅相信本地缓存，可能重复导出已入库报表 | 所有联网启动先回读云端原件；只有明确缺文件才进入平台操作 |
| 京东结算 | 重启后不重新打开同一任务的分片弹窗，下载无法续取 | 恢复已核验任务；等分片出现；丢文件至少两分钟后只重下一次同一分片 |
| 美团商品 | 再次点击商品标签包含隐藏副本；按天切换后未确认 | 仅定位可见标签，验证统计粒度真实生效 |
| 扩展协议 | 普通模拟测试可通过，实机却不认识新DOM读取函数 | AST扫描实际生产采集文件，全部20处读取调用通过真实RemoteLocator白名单验证 |
| 空表重取 | 空报表与所有门店未匹配混用错误码；信任客户端错误原因 | 后端独立解析原件，区分真空表/门店未绑定；旧授权重新核验，策略版本2 |
| 数据验收 | 空收入转成0；缺营业原件也认零销量 | 同日营业原件SHA、数据回读和明确零销量证据缺一不可；负费用与销量分开 |
| 归属与看板 | 只查原始层、遗漏看板层或内部门店错绑 | 核对原始表、实际看板表、内部store_id及金额数量；空原件还须检查后续冲突行 |

保留已有麦地店资质恢复豁免和用户确认的精确日期无销量例外，不将其他空值自动豁免。历史范围扩大需使用既有受验证的原件修订流程，不能把范围校验失败当缺文件重导。

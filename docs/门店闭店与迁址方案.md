## 0. 三条业务口径（业务确认，改代码前先读这里）

1. **「同一家店」= 同一个老板对同一家门店的运营。**
   换法人但门店**没有停止营业**，**不算闭店** —— 只在门店履历里记一条「法人变更」。
2. **迁址一律「老店闭店 + 新建门店 + 双向关联」。**
   收银机构编码在迁址后**会变**（业务确认），因此新旧两店**各自只记自己的数据**，
   **不做跨店合并口径**；关联仅作「凭证 / 追溯」：知道这家店不是全新门店、以及它从哪家店迁来。
3. **状态只有三态：`筹建中` / `正常营业` / `已闭店`。**
   「迁址」是**闭店原因**（`closed_type`），不是状态。
   历史遗留写法 `闭店`、`迁址` 在读取时一并视为已闭店（`lib/store-lifecycle.js` 的 `CLOSED_STATUS_ALIASES`）。

另有一条硬规则：**闭店前该店在职员工必须全部处置完毕**（随迁 / 调岗 / 离职），否则拒绝闭店。

## 1. 为什么不做「同店合并口径」

曾考虑过给迁址链加 `chain_id`、让报表支持「按系列（含迁址）合并」。业务明确否掉了：

> 新店只记录新店数据，只是后台需要有一些关联凭证，知道这个店不是全新门店、以及是哪个店迁址过来的。

所以最终方案**不引入 `chain_id`**，只保留：
- `stores.relocated_from_store_id` / `relocated_to_store_id` 双向指针
- 门店履历里互指的「迁址迁出 / 迁址迁入」两条事件（带 `details_json` 互指）
- 可上传凭证（闭店通知 / 租约 / 迁址协议）

「是不是全新门店」不额外加字段 —— `relocated_from_store_id IS NOT NULL` 即迁址店，单一事实来源。

## 2. 数据模型

### 2.1 `stores` 新增 5 列

```sql
closed_date               TEXT    -- 闭店日期
closed_type               TEXT    -- 闭店类型（固定枚举）
closed_reason             TEXT    -- 自由文本原因
relocated_to_store_id     INTEGER -- 老店填：迁到哪家店
relocated_from_store_id   INTEGER -- 新店填：从哪家店迁来
```

> **为什么闭店信息同时放在 `stores` 和履历表里？** 这是项目**既有的一致做法**
> （`employees.probation_date`/`leave_date` 与 `employee_lifecycle_events` 也是这样并存）：
> 履历表是**不可覆写的留痕**，`stores` 是**当前态**。列表筛选与统计卡片读当前态，
> 不必每次 join 聚合；真值以履历表为准，`stores` 上的可重算。

### 2.2 `store_lifecycle_events`（门店履历）

模式与 `employee_lifecycle_events`（员工生命线）完全一致，只增不改：

```sql
id, store_id, event_type, event_date,
old_value, new_value, note, source,
attachment_url, attachment_name, details_json, created_at
```

`event_type` 取值：`开业 / 闭店 / 重开 / 迁址迁出 / 迁址迁入 / 更名 / 法人变更 / 店型变更 / 区域调整 / 店长变更 / 资料变更`

### 2.3 闭店类型（固定枚举）

`迁址 / 租约到期 / 经营不善 / 商场物业调整 / 其他`

放在 `lib/store-lifecycle.js` 的 `CLOSED_TYPES`，前端通过 `GET /api/store-lifecycle/meta` 取，避免两处硬编码。

### 2.4 「闭店门店」系统分组

- `store_regions` 新增 `code` 列 + 唯一索引；种子行 `(name='闭店门店', parent_id=NULL, sort_order=9999, code='closed')`
- **全国统一的一个独立分组**，不挂在任何省市区下
- 闭店时把门店**移入**该组，因此它自然从原区域树里消失
- 后端**禁止改名 / 改层级 / 删除**该分组
- 区域选择器与门店分组编辑里都**不允许手工**把门店放进去或拿出来（进出只能靠闭店 / 重开）

> ⚠️ 实现坑（已踩过）：`code` 列的 `ALTER TABLE` 必须紧跟 `store_regions` 的**建表之后**。
> 早先把 ALTER 放在 `stores` 段（即建表之前）时，对全新库会因「表不存在」失败，
> 随后种子里的 `SELECT ... WHERE code=...` 引用不存在的列同样失败 —— **两处都被 `try/catch` 静默吞掉**，
> 结果是「列在、种子行永远不出现」。现已改为就地 ALTER，且失败时打印告警而不是静默。
> 同类坑：`lib/db.js` 内部的 `db` 是 sql.js 原生对象，**没有 `queryOne` 方法** ——
> 必须用同文件末尾的模块级包装函数 `queryOne/insert/run`。

## 3. 流程

### 3.1 闭店

1. 填 **闭店日期 + 闭店类型 + 原因**，可上传凭证
2. **员工处置清单** —— 该店**在职**员工逐人三选一：
   - **调往其他门店**（选目标门店）
   - **离职**（离职日期取闭店日期）
   - （迁址场景下另有「随迁到新店」，默认选中）
3. 校验通过后（有人未处置则整批拒绝并返回待处置清单）在一个事务里：
   - 处置员工（改 `employees.store_id/store_name`，或置离职），**各写一条员工生命线事件**
   - 写 `status='已闭店'` + 5 个闭店字段
   - **移入「闭店门店」分组**，并把**原区域记进履历的 `details_json`**
   - 解除店长绑定（`store_manager_assignments`）
   - 写一条「闭店」履历事件

> **在职判定以 `leave_date` 为准**（项目里 `deriveEmploymentStatus` 就是用它推导的）。
> 已离职的旧员工不必处置 —— 他们离职时就挂在这家店，属历史事实。

### 3.2 迁址（一键两步）

`POST /api/db/stores/:id/relocate`：

1. 建新门店，**默认继承老店的**：店型 / 法人 / 收款性质 / 区域归属
   （业务确认「默认继承老店可以，不对我自己再微调」）
   - **地址类字段一律不继承**（省市区 / 详细地址 / 经纬度 / 开业日期）——
     迁址本就意味着地址变化，预填旧地址反而会误导
2. 新店写入 `relocated_from_store_id`；若老店原本在某末级区域，新店**继承该区域归属**
3. 老店按「已闭店（迁址）」结束并移入闭店门店分组，写 `relocated_to_store_id`
4. 两边各写一条互指的履历事件（`迁址迁出` / `迁址迁入`），`details_json` 带对方 id 与新旧地址
5. 员工处置：**「随迁到新店」为默认动作**，也支持调往他店 / 离职

### 3.3 重开

`POST /api/db/stores/:id/reopen`：清空闭店字段、状态改回正常营业，
**从最近一条闭店/迁址迁出事件的 `details_json.previous_region_id` 恢复原区域归属**，
写一条「重开」事件。若找不到原区域记录，提示到区域管理里手工指定。

### 3.4 删除保护（防绕过）

- `PUT /api/db/stores/:id` **不允许**把 `status` 直接改成闭店或从闭店改回 ——
  否则「员工必须全部处置」与「重开恢复原区域」两条硬规则都会被绕开，接口会引导走专用操作
- `DELETE /api/db/stores/:id`：**有经营数据的门店禁止删除**
  （员工 / 营业数据 / 品项销售明细 / 商品销量 / 记账流水 / 成本核算 / 运营成本 / 门店日报 / 平台绑定），
  返回明确的阻断原因并提示改用「闭店」。
  无经营数据的空门店（多为建错的）可删，会连同自己的履历一起清理。
  > 本项目的 `ON DELETE CASCADE` **实际不生效**（历史遗留，见 `PROJECT_CHANGES.md`），
  > 所以关联行必须**显式删除**，否则会留下孤儿行（表现为「闭店门店组显示 1 家、点进去却没人」）。

### 3.5 启动自愈

`lib/db.js` 的 `init()` 每次启动幂等清理门店孤儿关联行：
`store_region_members` / `store_manager_assignments` 中 `store_id` 已不存在的行。

## 4. ⚠️ 导入匹配：闭店门店不能被“猜”走数据

`lib/business-analytics.js` 的 `resolveStore()` 是**导入时按名称识别门店的唯一入口**，
它原先的最后一层是**包含式模糊匹配**。闭店门店记录仍留在 `stores` 表里（历史数据要引用它），
所以必须分层处理：

| 层 | 规则 | 理由 |
|---|---|---|
| ① 显式 `store_id` | 一律按 id 返回 | 调用方明确指定（补录历史数据） |
| ② 精确 / 去空格归一化名称 | **允许命中已闭店门店** | 名称精确说明数据就属于那家店；闭店不等于这笔历史数据不存在 |
| ③ 包含式模糊兜底 | **只允许命中未闭店门店** | 模糊本身就是猜测，猜给已结束营业的门店会造成静默错位 |
| ④ **顺延保护** | 若输入**更精确地**命中某家已闭店门店（闭店名是输入的子串、且比命中的在营门店名更长），**返回 null** | 例如报表写「…方洲店旧址」，它同时包含在营的「…方洲店」；宁可不匹配交人工确认，也不要顺延猜给近名的在营门店 |

单测：`_tmp/verify-store-matcher.js`（10/10，用内存假 db，不触碰真实库）。
`resolveStore` 已为此**导出**，便于回归时直接覆盖这条规则。

## 5. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/store-lifecycle/meta` | 枚举：状态 / 闭店类型 / 事件类型（前端据此渲染，避免硬编码） |
| GET | `/api/db/stores/:id/lifecycle` | 门店履历 + 当前分组 + 迁址前后两跳 |
| POST | `/api/db/stores/:id/close` | 闭店（校验员工处置） |
| POST | `/api/db/stores/:id/relocate` | 迁址（老店闭店 + 建新店 + 双向关联） |
| POST | `/api/db/stores/:id/reopen` | 重开（恢复原区域） |
| POST | `/api/store-attachments` | 门店凭证上传（PDF/图片，≤10MB，按 sha256 去重） |
| GET | `/api/store-attachments/:file` | 凭证读取（内联预览） |

统计口径：`/api/db/stores/stats` 新增 `closed_by_relocation_count`（因迁址闭店）、
`relocated_in_count`（迁址而来的门店）、`newly_opened_count`（= 总数 − 迁址而来，即真正的全新开门店）。

权限：门店凭证走 `store.manage`（`lib/permissions.js` 新增规则）。
`/api/db/stores` **故意不加**接口级权限 —— 门店清单是十几个功能共用的下拉数据源，
按模块拦接口会让有权限的功能整块空白（见 `lib/permissions.js` 顶部的分层策略）。

## 6. 界面

- **门店基本信息**（`StoreBasic.vue`）
  - 状态三态；统计卡片新增「已闭店」，并说明其中几家是迁址而来
  - 列表新增「闭店」列（日期 + 类型标签）；迁址店在店名旁标「迁址而来」；闭店行灰化
  - 行内「更多」：门店履历 / 发起迁址 / 闭店（已闭店门店则显示「重开」）
  - 闭店与迁址共用弹窗：日期、类型、原因、凭证上传、**员工处置表**
  - 通用编辑弹窗**不提供「已闭店」**，只提供筹建中 / 正常营业
  - 门店履历抽屉：状态与分组摘要、**迁址关联可互相跳转**、时间轴（含凭证链接与来源）
- **门店区域管理**（`StoreRegionManage.vue`）
  - 区域树里**默认隐藏**「闭店门店」分组，用「显示闭店门店（N 家）」开关打开
  - 默认隐藏闭店门店；显式按「已闭店」筛选或打开开关时才显示
  - 系统分组不可编辑 / 不可新建下级；已闭店门店的分组「编辑」按钮置灰为「闭店中」
- **门店选择器**（`StoreRegionSelect.vue`）：默认不列已闭店门店，也不显示「闭店门店」分组

## 8. 遗留与建议

1. **`store.close` 独立权限码**：闭店是不可逆且影响历史口径的动作，目前与其他门店档案变更共用
   `store.manage`。建议后续按 `docs/岗位权限长期迭代计划.md` 的清单单独出一个权限码，
   并考虑强制填写原因 + 上传凭证（对标员工敏感字段的处理）。
2. **平台绑定不继承**：迁址后新址在美团/京东/抖音通常是新门店，需要重新绑定；
   老店的绑定保留历史。目前靠人工到「门店平台」页维护，未做联动提示。
3. **报表口径**：按业务决定不做跨店合并，因此迁址店在报表里表现为「新店无历史」。
   这是**有意为之**，不是缺陷；若将来业务改口要合并口径，再补 `chain_id`。
4. **闭店门店在历史报表选择器里不可选**：若某天需要「按日期查闭店门店的历史数据」，
   给 `StoreRegionSelect` 加一个 `includeClosed` 属性即可（改动很小）。
5. **无存量数据迁移负担**：功能上线时全库 25 家门店都是正常营业/筹建中，**历史上没有任何闭店或迁址记录**，
   所以本次是纯新增，没有历史数据要回填。

# 系统落地清单：把「品牌」做成一个独立的数据维度（对齐 M4）

> 状态：**草案，未改动任何代码** ｜ 定位：证明「组织不分开」在系统上的代价很小，并给出前置阻塞与上线顺序
> 关联文档：`docs/岗位权限长期迭代计划.md`（**M4：支持品牌、区域、门店的数据范围**）、`docs/组织权限与员工入网方案.md`（三层权限、股东域、越权点清单）、`docs/双品牌整合/01-双品牌总部组织与权责方案.md`

---

## 0. 一句话结论

「组织不分开」在系统上的代价，只是**给门店加一个品牌维度、并让 scope 校验认它**——不是建第二套系统、第二个企微主体、第二套权限。

你们 M4 本来就要做这件事，**本清单就是 M4 的前置数据地基**。

---

## 1. 三个前置阻塞（按依赖顺序）

| # | 阻塞 | 现状 |
|---|---|---|
| 1 | **门店品牌归属字段不存在** | `stores` 无品牌列；`lib/` 内无品牌实体（仅 `business-analytics.js` 一句注释提到"品牌子视角"） |
| 2 | **粤香园门店不在本系统** | 全库检索「粤香园」**零命中**；2026-09-21 快照 25 家店全部为鹅太公烧鹅 |
| 3 | **股东归属仍未录入** | `组织权限与员工入网方案.md` §5.0.1 记录的第一优先级阻塞项（25 店映射表） |

**三者不齐，品牌报表与品牌权限都做不出来。** 建议把 #1 与 #3 合成**一次业务录入**（一张门店台账，列：门店 / 品牌 / 股东 / 区域 / 形态 / 系统）。

## 2. 数据模型草案

- **新建 `brands`**：品牌码、名称、所属主体、特许经营备案号、状态、生效日期
- **门店归属独立成表，并带生效日期**（参照对 `store_ownership` 的建议）：

  `store_brand(store_id, brand_id, effective_from, effective_to, source)`

  > 翻牌店很常见（鹅太公 ↔ 粤香园）。不带生效日期，历史报表会随"当前品牌"错乱——与 `组织权限与员工入网方案.md` §9 待确认第 6 条对股东归属的提醒是同一类问题。

- **门店属性是四个正交维度**：`{品牌, 股东, 区域, 经营形态}`。

  `组织权限与员工入网方案.md` §5.1 已经证明「区域与股东不能合成一棵树」（同一 region 下并存不同股东的门店）。**品牌同理，绝不能挂进区域树**——同一区域内必然同时存在两个品牌的门店。

- **编码规范**：门店编码带品牌位（示例：`ETG-SZ-001` / `YXY-HZ-014`），但**不要改现有 `store_N` 主键**，用「展示编码 / 外部编码」字段承载，避免动历史数据和所有已有外键。

---

## 3. 权限 scope 规则（复用既有三层模型）

- 用户 scope = **{品牌集合} × {股东域} × {门店集合}**，**取交集**；跨品牌或跨股东默认 403。
- 总部职能（供应链 / 财务 / 人力）需要**跨品牌**看数 → 显式授"全品牌"，**不能靠"未绑即全部"**（现行 `storeScope()` 未绑门店返回 `null = 全部门店`，方向是错的，见 §6 #3）。
- 品牌管线负责人 = 本品牌 ∩ 本股东范围；督导 = 本品牌 ∩ 本区域。
- 报表与服务端必须走**同一个** `scopeGuard`，不能只在菜单隐藏按钮。

---

## 4. 品牌字段要贯穿的模块

门店 → 菜品与成本（`poultry_*` 禽类模型可按品牌出成，粤香园同样做烧腊，模型可直接复用）→ 记账 → 人事 → 协同事项与通知 → 权限与岗位 → 美团/外卖数据导入（`_handover/syncbot-current/meituan-rules.json` 的门店名映射要带品牌位）→ 经营分析（复用既有口径：「门店、品牌、平台三个子视角复用同一筛选范围」，见 `lib/business-analytics.js:2296`）。

---

## 5. 上线顺序（最小可验证）

1. `brands` + `store_brand` 建表与录入（先 25 店，再粤香园）
2. 门店与报表接口返回品牌并支持筛选（**只读，无权限变更**——先把数据跑通）
3. 权限 scope 引入品牌维度（先在一个岗位试点：运营专员）
4. `scopeGuard` 服务端强制 + 跨品牌越权验收
5. 企微侧：部门 / 标签 / 微盘共享空间按品牌 + 股东重构（**先核实主体数量**，见 `01-双品牌总部组织与权责方案.md` §1.3）

---

## 6. 安全前置（必须在品牌维度上线前或同批完成）

`组织权限与员工入网方案.md` §6 #8：`/api/staff` 零范围过滤且 `SELECT e.*` 返回身份证、银行卡等字段，而「门店店长」岗位带 `staff.view`。

**整合把两个品牌、四个股东的数据放进同一个库之后，这条的后果会成倍放大。** 品牌维度上线必须与它同批，或排在它之后。

---

## 7. 验收口径

对齐 `岗位权限长期迭代计划.md` 的「重大更新必做清单」六条，另加三条本次专有验收：

1. **跨品牌越权**：用鹅太公的账号请求粤香园门店的营业额与人员档案 → 必须 403；
2. **报表口径自洽**：同一天同一指标，「品牌视角」之和 == 「全平台视角」；
3. **写入不串**：品牌 A 的账号在品牌 B 的门店上没有任何写入能力（直接构造请求验证，不经过界面）。

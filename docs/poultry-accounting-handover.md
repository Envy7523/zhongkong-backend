## 1. 业务背景

「鹅太公烧鹅」是连锁烧味店（21+ 门店）。门店每天手工记录**整鹅消耗只数**并上报，但那是人工统计。老板要的是：
**能不能从收银系统的菜品销量，自动反推出某门店某时间段的禽类消耗只数**，用来对账、控损、估算成本。

已确认的事实基准（用于校准算法）：
- 欧景花园店 2026-09-01 ~ 09-10，门店日报记录 **80 只鹅**
- 该店当期菜品销量 2,079 份（收银流水，已核对无重复导入）
- 本项目算出来 76.5 只（覆盖率 32.5% 时）→ 与 80 只差 4.4%

## 2. 必须理解的领域知识（踩坑都源于这里）

### 2.1 一只鹅怎么拆

```
一只鹅 = 1 只 = 2 个半只 = 2 个上庄 + 2 个下庄
上庄 = 上半身的 1/4    下庄 = 下半身的 1/4
→ 2 个上庄 = 1/2 只，2 个下庄 = 1/2 只，合计 1 只 ✓
```

### 2.2 「一份占整只」与「一只出几份」是倒数关系（**最大的坑**）

| 说法 | 数值 | 含义 |
|---|---|---|
| 「一只鹅出 2 份上庄」 | 2 | **数块数**：上半身切成 2 块 |
| 「一份上庄是 1/4 只鹅」 | 1/4 | **说份量**：一份占整只的比例 |

两者都对，但**系统的字段必须用「份量」**：

```
「一只出几份」= 1 ÷ 一份占整只的比例
上庄 1/4 只 → 填 4     半只 1/2 只 → 填 2     整只 → 填 1
```

**填 2 相当于说「一份上庄吃掉半只鹅」，会把同一只鹅在上庄、下庄里各算一次，结果虚高近一倍。**
用户最初就填了 2，欧景店算出 118.5 只（实际 80 只）。改成 4 后变成 78.7 只。

页面已加防呆（`MenuAccounting.vue` 的 `portionShareText` / `portionWarning`）：
- 表格新增「一份占整只」列，把数字反算成份量显示（4 → `1/4`，1 → `一整只`，副产品 → `随鸟附带`）
- 表格新增「配置检查」列：身体类部位若「一份 ≥ 半只」且名称不含 整只/半只，弹出具体修改建议

### 2.3 其余部位是「一鹅多售」

头颈 1 只/鹅、翅 2 只/鹅、腿 2 条/鹅、腩 1 份/鹅、鹅肉（切片做饭/濑粉）约 11 份/鹅。
用户口径：**「其余都一鹅多售」**。

### 2.4 部位的两类性质（料篮模型的依据）

- **身体类**：整只 / 半只 / 上庄 / 下庄 / 腿 / 腩 / 切片肉 —— 都从同一块身体上取，**互相抢鸟 → 需求相加**
- **副产品**：翅 / 头颈 / 掌 / 杂 / 肝 / 肠 —— 一只鸟同时就产出，**不额外占鸟 → 需求取最大**

### 2.5 现实中的模糊之处（已知，暂未建模）

- **鹅腿有时混进鹅肉/小料**：腿饭卖不掉就把腿切片做鹅肉饭。当前按「腿」和「肉」两个独立份额相加处理，属近似。
- **腩的份量占比未定**：用户说「一只鹅只有一份鹅腩」（数块数），但份量占比未给，目前填 4（= 1/4 只）。

## 3. 数据模型

四张表，定义在 `lib/db.js`（`createTables()` 内，`menu_cost_components` 之后）。

### `poultry_birds` 禽类档案
| 字段 | 说明 |
|---|---|
| `animal` | 鹅 / 鸭 / 鸡 |
| `breed_name` | 品种名（如「清远黑鬃鹅」），唯一 |
| `net_weight_kg` | 单只净重，用于折重 |
| `unit_cost` | 单只成本，用于理论成本 |
| `status` | 启用 / 停用 |

### `poultry_yields` 整只出成拆解
| 字段 | 说明 |
|---|---|
| `bird_id` | 归属禽类 |
| `part_name` | 部位名（同品种内唯一） |
| `parts_per_bird` | **一只出几份**（= 1 ÷ 一份占整只比例） |
| `part_kind` | **身体 / 副产品**（决定相加还是取最大） |
| `part_weight_g` | 单份克重（可选，用于与折重交叉校验） |

### `poultry_dish_usage` 菜品耗用
| 字段 | 说明 |
|---|---|
| `menu_item_id` | 本地菜品 |
| `yield_id` | 部位 |
| `usage_qty` | **每份该菜品耗用几个该部位** |
| UNIQUE | `(menu_item_id, yield_id)` —— 一菜可挂多行，天然支持双拼/套餐 |

### `poultry_consumption` 实际消耗只数
| 字段 | 说明 |
|---|---|
| `store_id` / `store_name` / `date` | 门店 + 日期（`YYYY-MM-DD`，**按天录入**） |
| `bird_id` | 品种 |
| `quantity` | **实际消耗只数**（不是采购量） |
| `remark` | 备注 |
| UNIQUE | `(store_id, date, bird_id)` —— 手动录入，同键覆盖 |

> ⚠️ **口径（2026-09-15 定案，勿改回「采购」）**：
> 采购量（进货）受库存进出影响 —— `实际消耗 = 期初剩余 + 期间采购 − 期末剩余`，
> 与模型算出的「理论消耗」口径不一致，两者相减出来的差是库存波动、不是模型误差。
> 所以录入并参与对比/校准的必须是**门店实际消耗只数**；采购只数至多作参考，不进计算。
> 旧表 `poultry_purchases`（按月、含 amount）已废弃并 DROP，仅有的 15 行是孤儿残留。

> ⚠️ **`PRAGMA foreign_keys=ON` 在本项目实际未生效**（实测返回 0），所以所有 `ON DELETE CASCADE` 都不执行。
> 删除菜品会留下孤儿 `poultry_dish_usage` 行。本功能已用 `purgeOrphanUsage()` 在 `deleteBird` / `deleteYield` 前显式清理，
> 且 `listBirds` 的挂菜数改成 JOIN `menu_items` 只算还存在的菜品。**项目级隐患未修**，见 §9.7。

## 4. 核心算法（料篮模型）

实现在 `lib/poultry-accounting.js` 的 `calculate()`。

```js
// 1) 按 (菜品编码, 名称, 规格) 聚合销量，排除退款行
//    WHERE refunded NOT IN ('部分退','是','1')
// 2) 每条流水匹配本地菜品（三级兜底，见 §5）
// 3) 按「禽 + 部位」汇总需求
demand_p = Σ(该部位的菜品销量 × usage_qty)

// 4) 分两类汇总
body_birds     = Σ_{p ∈ 身体}   demand_p / parts_per_bird_p     // 相加
byproduct_birds = max_{p ∈ 副产品} (demand_p / parts_per_bird_p)  // 取最大

// 5) 只数（保留 2 位小数）
N = max(body_birds, byproduct_birds)

// 6) 折重 / 成本（先定稿只数再推，保证页面上「只数 × 净重/成本」能对上）
weight_kg = N × net_weight_kg
cost      = N × unit_cost
```

**为什么不能全部取最大**：整只 / 半只 / 上庄 / 下庄 是同一块身体的**互斥卖法**（卖了整只就不能再卖它的下庄），
取最大会把它们当成同一批鸟，结果严重偏低（实测 7,497 只 vs 正确 20,646 只）。

**为什么不能全部相加**（早期实现）：等于假设每个菜品各买一只鸟，把同一只鸟的多个部位重复计鸟
（实测欧景店虚高 118.5 vs 78.7；全公司虚高 14,209.88 vs 6,586.74，约 2.11 倍）。

### 附带输出（供页面使用）
- `summary.birds[]`：`birds_count`（新口径）、`birds_count_linear`（旧口径参考值）、`body_birds`、`byproduct_birds`、`governing`/`governing_part`（瓶颈在身体还是副产品）、`weight_kg`、`cost`、`risk`
- `parts[]`：部位汇总（部位/类别/一只出成/总需求/折鸟数/`is_bottleneck`）
- `dishes[]`：按菜品的明细行（`birds_count` 是**线性贡献**，`share` 按线性口径合计 100%）
- `coverage`：未绑定 / 已绑定未配系数 / 复核提示
- `summary.poultry_*` 与 `coverage.poultry_scope`：**禽类菜口径**（两个覆盖率、缺口清单、菜品级判定）见 §9.1.1

## 5. 菜品匹配三级兜底

收银流水的 `(product_code, product_name, spec)` 分组依次尝试：

1. `dish_sales_mappings` 绑定表（按 编码 + 名称 + 归一化规格）
2. 名称 + 归一化规格 直配 `menu_items`
3. 同名唯一命中
4. 都未命中 → 落入 `coverage.unbound`（未绑定清单）

**两条硬规则（都是踩坑补的）**：
- **空菜名不得参与任何名称匹配** —— 报表/档案里的空名行会互相误挂
- **孤儿绑定视为未绑定** —— `dish_sales_mappings` 指向已被删除的菜品时（库里有 10 条历史遗留），
  不能算「已绑定」，否则缺口清单会出现没有菜名、也无法去配置的空行；应退回名称兜底

归一化规格：`normalizeDishSpec()`，`'--'` 与空串统一为 `''`（与 `dish_sales_mappings` 唯一键口径一致）。

## 6. 已确认的口径决策（用户拍板，勿擅自改）

| 决策点 | 结论 |
|---|---|
| 换算模型 | **整只出成拆解（料篮）**，不用简单的菜品耗用系数表，也不复用 `menu_cost_components` |
| 渠道 | **全部渠道**，页面上可再筛选 |
| 退款 | **整行排除**（报表只有退款金额、无退菜数量，无法精确扣减） |
| 覆盖率缺口 | 结果页**显著提示覆盖率** + 未配清单可下钻 |
| 输出内容 | 只数汇总、折重与理论成本、按菜品下钻、理论 vs 实际采购对比 |
| 采购数据 | **手动录入**（每店每月每禽类），不做 Excel 导入 |
| 出成数据录入 | Excel 模板导入 + 页面手工微调（模板预填本地全部菜品） |
| 时间区间 | 默认本月，支持自定义起止日 |
| 只数精度 | 保留 2 位小数 |

### 渠道判定
`dish_sales.payment_detail` 关键字，优先级 **团购 > 外卖 > 堂食 > 其他**：
- 团购：含「团购」（`店内销售|收银POS|POS|抖音团购` 属团购核销，不是纯堂食）
- 外卖：含「淘宝闪购」「京东」「外卖」
- 堂食：含「店内销售」「收银POS」「扫码点餐」「小程序」「堂食」
- 其他：都不含 → 归「其他/未分类」

> ⚠️ 实测**约 65% 销量**（全公司 17.5 万份）的 `payment_detail` 形如「扫码支付-微信 25.00」，
> **不含任何渠道信息**，全部落到「其他/未分类」。所以渠道筛选可用，但别指望它覆盖全部销量。
> 页面已单独标注这一点。

**批量关联的两种模式**（用户要求，勿合并）：
- `replace` 覆盖：先清空这些菜品的原有配置（适合整组用同一套部位），并**回报被清掉的条数 `removed` / 受影响菜品数 `replaced_dishes`**，避免静默删掉手工配置
- `append` 追加：upsert 保留原配置（适合给已有配置的菜再加一条双拼部位）

### 8.1 风控（食材去向对账）

原理：一只禽固定产出 1 个头颈 + 2 只翅 + 一整只身体的肉，三者来自同一批鹅，**记录必须互相吻合**。

以模型只数 `N` 为基准，算「应有 − 实际」：
```
身体：应有 N 只份量 → 实际 body_recorded → 差额 = N − body_recorded
副产品 p：应有 N × parts_per_bird_p → 实际 demand_p → 差额
```
两重校验：
- **副产品 ↔ 身体**：头颈说加工 100 只、身体只记录 90 只份量 → 10 只份量的肉去向不明
- **副产品 ↔ 副产品**：头颈反推 100 只、翅反推 30 只 → 必有一方没绑全/没记录（`byproduct_conflict`）

**必须做防误读**：覆盖率低时「身体差额」主要由未绑定菜品造成，不是损耗。
页面在覆盖率 < 90% 时强制显示橙色告警说明这一点。

实测（全公司 5/1–9/10）：`N = 6,749`（头颈反推），身体只记录 4,444.14 只份量 → 差 **2,304.86 只份量（34.2%）**；
头颈反推 6,749 vs 翅反推 756 → 差 5,993 只（翅相关菜品大面积没绑定）。

### 10.1 「云上数据为准」时怎么把云上整库换成/合并到本地（2026-09-14 实操过一遍）
场景：用户在**云上**录了/导入了新数据（外卖账单、记账本），本地落后，要求"以云为准"。

**关键教训：不要盲目整库覆盖。** 用户手工做出来的业务判断（标定的系数、本地独有的成本构成）
在云上**没有对应版本**，一覆盖就永久丢失。所以流程必须是「先逐表逐行比对 → 再覆盖 → 再写回本地独有值」。

```powershell
# ① 拉云上库（SSH 被封时先解封；本机出口 IP 被 sshd 惩罚/ fail2ban 拦时表现为"TCP 连上但不发 banner"）
python -u _tmp\pull-cloud-db.py --wait-minutes 300 --interval 60   # 自动等解封 + 下载 + sha256 校验
node _tmp\inspect-db.js _tmp\cloud\database.sqlite                # integrity_check / 表数 / 关键行数

# ② 逐表逐行比对（换库前的「影响面清单」，务必先看清楚）
node --max-old-space-size=6144 _tmp\diff-db.js data\database.sqlite _tmp\cloud\database.sqlite --summary-only
node --max-old-space-size=6144 _tmp\local-only-summary.js          # ⚠️ 补「行数不同」表的行级比对
node _tmp\local-only-rows.js                                       # 配置类表逐条列出「仅本地」行
node _tmp\gap-report.js                                            # 面向用户的「云上有本地没有」清单

# ③ 换库（自动备份 + 清孤儿 + 写回本地独有值；dry-run 默认，加 --yes 才执行）
#    前置：必须先停后端（sql.js 整文件覆盖写，运行中的服务会把它覆盖回去）
node --max-old-space-size=6144 _tmp\swap-to-cloud-db.js --yes

# ④ 启动后端 → 跑只读回归
node _tmp\gap-report.js                                            # 应显示各项「云端独有 0」
node tools\poultry-verify\verify-risk-control.js
node tools\poultry-verify\crosscheck-poultry.js
```

⚠️ **`diff-db.js` 的一个坑**：它只在**行数相同**时才比内容，所以 `menu_items` 这种"行数也差、内容也差"的表
会被漏掉（本次就漏了 `#451.cost` 8.8 vs 0）。必须配合 `_tmp/local-only-summary.js` 一起看。

## 11. 验证方式

验证脚本已入库到 `tools/poultry-verify/`（`_tmp/` 被 gitignore，里面还有大体积数据库快照）。
所有脚本都是**非破坏性**的：只用自建临时数据（禽类名带「临时」前缀、临时菜品），收尾全部回收；
对真实菜品配置只做**只读校验**。
（2026-09-14 之前并非如此 —— 金丝雀脚本曾会改坏真实菜品，见 §9.8；现已修好并用金丝雀自证。）

| 脚本 | 项数 | 覆盖内容 |
|---|---|---|
| `verify-poultry.ps1` | 49 | CRUD、参数校验、核算不变量、Excel 模板/导入、门店/渠道筛选、采购对比 |
| `verify-poultry-batch.ps1` | 29 | 分组选菜、批量覆盖/追加、`removed`/`replaced_dishes` 回报、参数校验 |
| `verify-poultry-scope.ps1` | 41 | **禽类菜范围**：关键词 CRUD/停用/回读、显式名单三模式与优先级、已配耗用强制计入、双覆盖率 7 项自洽、收尾还原与基线断言（关键词表快照**自愈**） |
| `verify-risk-control.js` | 12 | 风控对账字段内部一致性、欧景店对上 80 只 |
| `verify-yield-append.ps1` | 13 | 复现「4 规格 → 绑定 → 追加到 6 规格」场景 |
| `crosscheck-poultry.js` | — | 直连 sql.js **独立复算**，与接口结果逐项比对 |
| `canary-safe-teardown.ps1` | 12 | 金丝雀：**用自己的临时数据**跑上面两个脚本，并用「运行前后全量逐菜品配置比对」证明真实数据未被改动（§9.8） |

**核算不变量**（接手后改算法必须仍然成立）：
1. 每行明细：`birds_count = round(销量 × 每份耗用 ÷ 一只出成, 2)`
2. 每个部位：`birds = round(该部位总需求 ÷ 一只出成, 2)`
3. **每只禽（资源约束模型，2026-09-13 升级）**：
   各资源池分别算需求只数，取**最大者**为总只数 ——
   `birds_count = max over r ∈ {body, leg, wing, head_neck} (该资源池需求 ÷ 每只供应量)`；
   `body` 池的需求 = 所有「身体」类部位折鸟之和（互斥卖法必须相加），
   `leg / wing / head_neck` 池的需求 = 各部位消耗条数之和（一只出 2 腿 / 2 翅 / 1 头颈）。
   瓶颈 = 那个最大的资源池，页面「瓶颈」列据此显示（如鹅常是 `腿·鹅腿`、鸭常是 `身体·单份`）
4. `total_birds = Σ 各禽 birds_count`
5. 每只禽只有一个 `is_bottleneck` 标注（即瓶颈资源池下贡献最大的那个部位）
6. `total_birds_linear ≥ total_birds`（线性口径是上限）
7. 明细 `share` 合计 = 100%（按线性口径）

运行示例：
```powershell
# PowerShell 脚本必须显式按 UTF-8 读取（本机是 PS 5.1，直接 -File 会把中文当 GBK）
$code = Get-Content -Raw -Encoding UTF8 'tools\poultry-verify\verify-poultry.ps1'; Invoke-Expression $code
node tools/poultry-verify/verify-risk-control.js
node tools/poultry-verify/crosscheck-poultry.js
```

## 12. 踩过的坑（改代码前务必读）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 消耗只数虚高 2 倍 | 早期口径 = 各菜品独立折鸟后**相加**，等于每个菜品各买一只鸟 | 改料篮模型：身体相加 / 副产品取最大 |
| 2 | 上庄填 2 导致虚高近一倍 | 「一只出几份」被当成**数块数** | 语义定为「份量占比的倒数」+ 界面加「一份占整只」列与防呆提示 |
| 3 | 全取最大后严重偏低 | 整只/半只/上庄/下庄是**互斥卖法**，必须相加 | 只对副产品取最大 |
| 4 | 缺口清单出现没菜名、无法操作的空行 | 报表/档案里的**空菜名行互相误挂** | 空名不参与任何名称匹配 |
| 5 | 同上（另一来源） | **孤儿绑定**（绑定表指向已删菜品，库里 10 条） | 孤儿绑定视为未绑定，退回名称兜底 |
| 6 | 采购对比恒为 0 | 采购按月存 `YYYY-MM`，查询却拼成 `YYYY-MM-01` | 用同一个 `YYYY-MM` 匹配 |
| 7 | 页面白屏/报错 | 「档案已加载但核算未返回」时读空 `summary` | 模板加 `v-else-if="result"` 守卫 |
| 8 | 新增的出成部位在下拉里选不到 | 部位下拉只加载一次，保存出成后没刷新；弹窗又只在「列表为空」时才拉 | 保存后刷新 + 每次打开都重拉 + 抽屉切页签也刷新 |
| 9 | 刷新/分享链接进入新页面落到「数据概括」 | `App.vue` 的 `workspaceRouteTabId` 漏登记独立静态路由（顺带发现 `/menu-management/category` 也有） | 在简单页面映射里补上两条 |
| 10 | 删品种时报「已被 N 个菜品引用」但那些菜品已不存在 | 外键级联未生效，耗用行成孤儿 | `purgeOrphanUsage()` + 计数改为 JOIN 存在的菜品 |
| 11 | **事故：验证脚本整表清空用户数据** | 脚本为「可重复执行」做了整表 DELETE | 改为只删自建行（名称前缀）+ 对真实菜品配置快照还原 + 金丝雀测试固化 |
| 12 | **事故：金丝雀脚本改坏真实菜品 206 却全 PASS** | 金丝雀把测试数据埋在**真实菜品**上，收尾是「清空」而非「还原」；断言只检查自己埋的数据，对真实配置被改坏**瞎** | 金丝雀改用自建临时菜品 + 运行前后**全量逐菜品配置比对**（§9.8） |
| 13 | 孤儿采购：15 条看不见的采购（12,000 只） | 脚本先删品种再回收采购，而 `listPurchases` 用 `JOIN` 把孤儿行**隐藏**了 → 回收找不到它们，UI 也看不见 | `LEFT JOIN` + `is_orphan` 暴露；`deleteBird` 顺带回收该品种采购；脚本改顺序（§9.9） |

> 第 11 条是真实事故：脚本收尾时删掉了用户当时手工录入的全部禽类档案/耗用配置/采购记录。
> **教训：验证脚本绝不允许整表 DELETE；删除范围必须一开始就限定在自己创建的行上。**
> 第 12 条是它的变体：**只限制删除范围还不够**，还要证明「没动真实数据」——
> 断言必须建立在「运行前基线」上（逐项比对），而不是「自己埋的东西还在」这种自证式检查。
> 第 13 条的教训：查询用 `JOIN` 会把垃圾**静默隐藏**，比报错更难发现；父行删除时不要依赖级联（§9.7）。

另外几个环境坑：
- 本机 `pwsh` 实际是 **Windows PowerShell 5.1**，`.ps1` 文件必须显式 `Get-Content -Encoding UTF8` 后 `Invoke-Expression`
- PS 5.1 的 `Invoke-RestMethod` **不按 UTF-8 编码请求体**，中文会变成 `?`，必须手动 `[Text.Encoding]::UTF8.GetBytes($json)`
- `node` 的 `child_process.spawn` 在受限沙箱下会 `EPERM`，vite 构建需要更宽权限
- 沙箱下 `Get-NetTCPConnection` / `taskkill` 可能不可用，用 `netstat -ano` + `Stop-Process` 替代

## 14. 术语表

| 术语 | 含义 |
|---|---|
| 料篮模型 | 一只禽 = 一个「料篮」，同时产出多个部位；需求按部位分别算，再按性质合并 |
| 身体类 / 副产品 | 部位的两类性质，决定需求相加还是取最大 |
| 一只出几份 | = 1 ÷ 一份占整只的比例（**份量口径**，不是块数） |
| 折鸟 / 折合只数 | 把某部位的份数需求换算成「需要多少只禽」 |
| 瓶颈部位 | 决定总只数的那个部位（身体合计与副产品最大中较大的一方） |
| 覆盖率 | 两个口径：① **禽类菜品覆盖率** = 已配销量 ÷ 禽类菜销量（风控看这个）② **全量覆盖率** = 已配销量 ÷ 全部销量（参考）。见 §9.1.1 |
| 禽类菜 | 判定见 §9.1.1 的五级优先规则；范围由「关键词表 + 显式名单」维护，可在页面调整 |
| 缺口 | 未绑定 / 已绑定但未配系数 / 需复核配置，三类 |
| 风控对账 | 用副产品反推加工只数，与其他渠道记录交叉校验，暴露「去向不明」 |

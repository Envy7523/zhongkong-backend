## 二、根因（两处叠加）

1. `lib/pos-daily-preview.js` L84–85：对**每一个**「正常营业」门店，只要当天没有
   `store_sales` 渠道记录、或没有收入构成记录，就 push 一条 problem。它没有区分
   「当天没录入门店」和「录了但数据不齐」。
2. `lib/pos-daily-push.js` L31 / L74：
   `if (!data.ready || !data.store_count) return { reason: 'pos_daily_data_incomplete', problems }`
   而 `ready = problems.length === 0`（preview 末尾）。于是只要有一家门店当天没数据，
   **整张收银日报就不生成**。

补充：排除名单 `excludedStores` 只由 `pos-daily-preview.js` 的 options 传入，
而线上唯一的调用方 `pos-daily-push.js: preview()` 从不传它 ⇒ 排除机制在实时链路里
实际是不可用的，只能靠改代码解决。

## 四、改动

```js
// 当天完全没有记录的门店（既无渠道记录也无收入构成）视为「当天没录入门店」：
// 按业务约定不报警、不阻塞日报，直接从高低位排名中略去；
// 只有「有数据但不齐」才算问题，避免把缺数据当成故障。
const rows = [...byStore.values()].filter(row =>
  Object.keys(row.channels).length || Object.keys(row.compositions).length);
for (const row of rows) {
  const hasStoreSales = seen.has(`${row.store_id}:store_sales`);
  const hasCompositions = Object.keys(row.compositions).length > 0;
  if (!hasStoreSales) problems.push(`门店缺少店内销售记录：${row.store_name}`);
  if (!hasCompositions) problems.push(`门店缺少收入构成记录：${row.store_name}`);
  ...
  if (hasCompositions && Math.abs(compositionTotal - row.recorded_amount) > 0.02)
```

## 八、混合场景验证（部分门店有数据 + 部分门店歇业）

构造：12 家有完整数据 + 3 家"歇业/未开业"（坂田、宜章、鹿城）+ 1 家"数据不齐"（只有外卖渠道）。

| 检查项 | 结果 |
|---|---|
| `ready` | `false`（**仅因数据不齐店**，非歇业门店） |
| `store_count` | **13** = 12 家有数据 + 1 家数据不齐 |
| 歇业门店是否出现在 problems | 坂田/宜章/鹿城 → **全部无（自动忽略）** |
| 数据不齐门店是否仍报警 | **是**（`缺少店内销售记录 / 缺少收入构成记录`） |
| 歇业门店是否进入排名 | **否** |
| 判定 | **PASS** |

结论：**"门店偶尔歇业一两天"无需报备**——当天无记录即自动忽略；
只有"录了但缺店内销售/收入构成"这类真问题才会报警。

## 九、仍需你确认的两点

1. **09-30 当天数据还没导入**：23 家门店全部为空。当天收银数据导入后，只要
   ≥9 家门店有数据即可生成；当前 `store_count=0` 时系统不会误报"缺记录"，但也**不会生成**（按设计）。
2. **排名口径**：现在"当天没录入门店"的门店**不进入高低位排名**（store_count 从 23 变 20）。
   如果报表希望仍显示这 3 家（金额按 0 计），这是另一种口径，需要你确认；当前实现按你
   "没有数据就不录入"的说法处理。
3. **三家店的真实经营状态**：坂田店、湖南宜章店、上排店连续多日无 POS 记录但仍为「正常营业」。
   若确已停业/未营业，建议改门店状态或纳入排除名单，这样"缺数据"与"真故障"才彻底分开。

# 人员管理界面重构方案

日期：2026-10-16。状态：用户已确认，并授权本地实现后上云。以下为确认时的设计方案，实际实现与部署结果另行记录。此前店长唯一性及新增入口的修复一并纳入本次交付。

## 1. 重构目标

同一个账号在一份人员列表中完成查找、编辑、授权和核对。页面主标题保留“人员管理”，副说明为“管理登录账号、岗位及负责门店”。

这份列表按账号身份组织，不将员工库中尚未开通账号的人自动创建为账号，也不按同名或手机号自动合并。已关联的员工档案提供只读摘要和跳转。

## 2. 已确认的重合与困惑

| 当前情况 | 拟调整 |
| --- | --- |
| 岗位分配与账号资料各有一份人员列表 | 合并为一份人员列表 |
| 查个人资料、岗位、权限需要切换列表找同一个人 | 点人员打开统一详情抽屉 |
| 旧账号编辑还带有岗位与单店绑定设置 | 岗位及门店统一通过同一个编辑器维护 |
| 网页与小程序作为两份人员视图，新增后容易被隐藏 | 默认显示全部账号，登录端作为筛选和标签 |
| “新增人员”“添加成员”“创建成员”称呼不一致 | 页面及流程统一为“新增人员” |
| 微信绑定申请长表混在账号目录下面 | 独立为“微信绑定申请”待办页签，显示待处理数 |
| 员工档案、账号岗位、权限模板容易混淆 | 明确三个管理入口的职责，互相提供跳转 |

## 3. 页面结构

人员管理保留两个顶层页签：“人员列表”和“微信绑定申请”。第二项是审批任务，不再展示另一份完整人员目录。

人员列表页只有一个固定的主按钮“新增人员”，位于右上角；“按门店查人员”是次级工具。进入详情后，新增入口仍留在页面原位，不藏入更多菜单。

```text
人员管理                                      [新增人员]
人员列表    微信绑定申请（待处理数）

搜索姓名/账号/手机号    岗位    负责门店/区域
登录端：全部    配置状态：全部     [查询] [重置]

人员 | 档案与归属 | 岗位及负责范围 | 登录端 | 微信绑定 | 配置状态 | 操作
张某 | 已关联…   | 督导：深圳12店  | 网页   | 已绑定   | 已配置   | 查看详情
     | 在职…     | 店长：欧景店    | 小程序 |          |          | 分配岗位
```

“档案与归属”显示劳动/组织归属，“岗位及负责范围”逐岗位显示授权范围，两者分别标注。多个岗位保持对应关系，不将所有岗位和所有门店各自拼成一段。

默认全部登录端，提供网页、小程序、双端、全部筛选；组织归属与权限岗位类别使用各自明确的标签，不互相推断。少用大面积统计卡和独立头像列，让列表首屏可见。

筛选编辑后点击查询才应用；重置恢复默认列表；返回详情前的列表时保留条件和分页。新增成功定位并突出新账号，如原条件会隐藏新人则明确提示并切回可见条件，避免无提示清空用户查询。

## 4. 一个人的统一详情

点击姓名或“查看详情”打开右侧详情抽屉，顶部固定姓名、登录账号、关联档案、在职状态和登录端摘要。

抽屉内部使用四个分区：

| 分区 | 可处理内容 |
| --- | --- |
| 账号资料 | 登录账号、显示名称、账号联系方式、头像；有网页登录权限时显示修改密码；微信绑定情况及跳转 |
| 岗位与门店 | 主岗位、兼任岗位、每个岗位的负责门店/区域、允许登录端、调整原因 |
| 实际权限 | 按网页/小程序查看最终生效功能、门店及来源；查某店某功能是否允许 |
| 变更记录 | 操作人、时间、原因、调整前后对照 |

行内“分配岗位”直接打开该人的“岗位与门店”，避免额外弹出另一套同类表单。“主岗位/兼任岗位”替代“主岗位/子岗位”，避免误解为岗位继承。

员工姓名、劳动归属、人事职位、薪资及入离职信息只作必要摘要；编辑这些内容跳转“员工管理”。抽屉不重复提供人事档案编辑器。

普通账号资料修改与权限调整分别标识保存范围。单次操作涉及多个字段时整体成功或整体回滚；保存失败保留输入并定位出错字段，不能显示假成功。

## 5. 统一新增流程

右上角“新增人员”进入三步流程：

1. **身份与登录**：选择已有员工档案，或明确选择“无员工档案账号”；已经关联账号的员工显示现有账号并引导查看，阻止重复关联。设置登录账号及网页/小程序登录端；仅小程序不要求网页密码，开通网页则设置初始密码。
2. **岗位与门店**：选择主岗位和兼任岗位，逐岗位指定负责门店/区域。岗位模板中没有开放的登录端不能因人员选择而自动获得。复制配置只复制授权内容，不复制密码、微信身份或员工档案关联。
3. **核对创建**：确认身份、登录端、岗位范围及必要的实际权限摘要，再创建。失败不留下半个账号；成功后显示新增结果，并可继续查看详情或新增下一人。

默认不猜测员工应该获得什么岗位或门店权限。人员页创建的是系统账号；需要新建员工档案时给出“去新增员工档案”链接，仍由员工管理完成。

## 6. 店长任命的特别处理

每店至多一名正式店长；店员、储备店长允许多人。同一账号可兼任多个岗位、负责多家门店。

选择正式店长岗位和门店时显示当前占用情况，例如：“欧景店已有店长张某”；冲突项就近提示，并提供“前往正式店长任命”入口。后台保存时继续复核，不能只依赖下拉选项禁用。

已有店长的交接沿用审批和生效日期流程，不在人员页增加“一键覆盖原店长”的旁路。集团督导权限、其他负责门店和历史业务记录按原规则保留。

## 7. 三个管理入口的职责

| 入口 | 管什么 | 与人员管理的关系 |
| --- | --- | --- |
| 员工管理 | 人事档案、劳动/组织归属、薪酬、入离职 | 人员详情提供受权限控制的档案跳转 |
| 岗位设置 | 岗位功能权限、分端权限、模板适用门店 | 分配时选择模板，模板修改仍回岗位设置 |
| 人员管理 | 账号身份、登录端、岗位分配、负责范围、微信绑定 | 本次重构对象 |

“微信绑定申请”页只完成核对本人、选择已有账号、批准/拒绝及查看处理结果；查看人员回到统一详情，不能在绑定审批中顺便授予岗位或扩大门店范围。

## 8. 兼容与视觉约定

旧账号继续兼容读取，未完成逐岗位范围配置的标注“待核对”，通过统一编辑器核对后保存。去掉旧前端岗位编辑表单不等于自动清除其已有配置，也不按账号旧单店字段猜出全门店权限。

保留原账号ID、员工关联、微信身份、审批及操作历史；重构不自动补权限或批量迁移人事身份。列表与操作权限沿用现有服务端校验，不因页面合并扩大可见范围。

沿用现有 Element Plus 组件、中文字体及主题色；采用清晰的筛选栏、适度紧凑表格和统一抽屉。主操作突出，修改密码、解绑及删除等放在明确分区；已有员工关联账号继续遵循保留历史身份的限制。表单必填、禁用原因、加载、空数据、查询失败、版本冲突均有文字反馈。

设计技能的通用检索包含营销页面建议，本方案只采用适合管理后台的可访问性、主操作唯一和状态清晰原则，不采用营销布局、外部字体或装饰动效。

## 9. 确认后的实施与验收

建议一次完成上述人员管理范围的本地重构，再由用户验收。

1. 合并人员列表及详情入口，移除重复表单，统一名称与新增流程。
2. 对接现有身份、授权、微信绑定和历史查询，补齐统一读取及保存所需的接口能力；具体服务端改动以实际代码为准，不先更换数据库模型。
3. 隔离验收：普通人员新增、仅小程序及双端、关联员工防重复、主/兼任与多店、店长冲突、旧账号核对、绑定批准/拒绝、筛选后新增可见、账号资料编辑不误改权限、越权及保存回滚。
4. 提供本地页面供用户确认。发布云端单独说明范围与验证结果；本次方案确认不自动等同于云端发布确认。

**确认结果：用户已同意采用“一份人员列表 + 统一个人详情 + 独立微信绑定申请队列”，并明确要求完成后上云。**
